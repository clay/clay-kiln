# Real-time collaboration

Kiln lets several people edit the same page at the same time. It turns on by itself when the site's amphora (9+) has [collaboration enabled](https://github.com/clay/amphora/blob/master/docs/advanced/collaboration.md); otherwise none of this runs and kiln behaves exactly as before.

## What editors see

* **Who's here.** Avatars of everyone else on the page sit in the toolbar, next to the site's buttons. A green dot means live; gray means reconnecting, with the tooltip "Reconnecting… your changes are still being saved." Someone with several tabs open shows once. Click the avatars for a list of who's doing what ("Editing Headline", "Typing in Paragraph", "Idle", "Away"), a **Show** button that scrolls to them, and recent changes ("Ada published the page").
* **Where they are.** Whatever someone has open gets an outline in their color with a name tag ("Ada is editing", a dashed outline while they type). If it's off screen, a pill at the top or bottom edge points to them; click it to scroll there.
* **Their changes, live.** Within a couple of seconds of someone saving, the component re-renders for everyone, highlighted briefly ("Updated by Ada"). Components they add or remove, reordering, publishing, unpublishing and scheduling all show up too ("Grace published this page").
* **Nothing moves under you.** A change to something you have open (or to the list around an inline field you're typing in) waits until you close it, then merges with your edit. Meanwhile the component you have open says so: "Ada changed this too · updates when you're done".
* **One person per field.** While someone is working on a field (they changed it in the last minute, with the tab in front), nobody else can open it: clicking it just says "Ada Lovelace is editing this". Once they've gone quiet (no changes for a minute, their tab is in the background or idle, or they've lost their connection), clicking it offers to take over: "Ada Lovelace has this open — Take over / Cancel". Taking over saves what Ada typed first, closes Ada's form, and tells Ada: "Grace Hopper took over Paragraph — your changes were saved" (shown once Ada is back, if that tab was in the background). Your form then opens with Ada's changes in it; meanwhile the field says "Saving Ada Lovelace's changes…". If it's open in your own other tab, you're offered "Open here" instead, whenever you like. *Different* fields of the same component are never locked; those changes merge.
* **No lost work.** If you both change the same field anyway (one of you was offline, or you both opened it within the same second or two), your save wins (you're the one saving) and a snackbar offers "Use Ada's" to switch to theirs. If someone deletes a component you were just editing, you're offered **Restore**.
* **Undo stays yours.** Undo and redo only step through your own changes; they never revert someone else's.
* **Offline, nothing is lost.** If the CMS can't be reached (you went offline, a network gateway or proxy is in the way, a deploy), saves wait instead of failing: your change stays on the page, a note under the toolbar says "Your latest changes haven't saved yet. They'll save automatically as soon as you're connected again.", and they go out, in order, as soon as a request gets through (kiln checks every few seconds, and right away when the tab gets focus or the browser comes back online). Closing the tab meanwhile asks first. This works with collaboration off too; with it on, a save that waited merges with anything someone else changed meanwhile.
* **Catching up after reconnecting.** If kiln may have missed changes (it was reconnecting, or the server says saves went through without anyone hearing about them), it quietly does what a reload would, in place: it re-reads the page and shows whatever changed with the usual highlight, "Updated by Ada", or "Updated while you were reconnecting" when nobody can be named. A component you have open waits, as above ("Ada changed this too · updates when you're done", or "Changed while you were reconnecting · updates when you're done"), and your save merges with it; if you both changed the same field: "Text was updated while you were reconnecting — kept your version · Use theirs". It never reloads the page, never interrupts typing, and never asks you to do anything; saving is never blocked. Anything it couldn't re-read is tried again a little later.

## How it works

On load, kiln reads `locals.collaboration` (added by amphora in edit mode) and starts a small polling loop (`POST /_collab/sync`: every 2s with others, 4s alone, 20s in a background tab, 30s when idle) that sends this tab's presence and receives everyone else's presence plus the page's change feed.

Saves carry the revision of the data they were built from (`X-Clay-Rev`). If someone else saved in between, amphora answers 412 with the current data (and, when its feed knows, who saved it last, so the notice can name them); kiln merges field by field (component lists by `_ref`, so adds/removes/moves from both people survive), retries, and then shows the merged result. Form saves only include the fields you actually changed.

Revisions only cover saves the server's store saw. Kiln **catches up** (`catchUp` in `remote.js`) whenever it may have missed changes: a sync answered 503 (the store was unreachable), the sync's `gap` changed (amphora starts a new gap whenever saves may have gone around the store, including on an instance that has since restarted), the page was rendered without a feed position, or one of this tab's own saves came back without a revision. It first forgets every revision it knows (so saves send `X-Clay-Rev: -1` and merge), then re-reads every component (a few at a time), the page and the layout, and applies what changed through the same path as anyone's change, learning fresh revisions as it goes. A component counts as changed only if a field people can edit (in its schema) differs: kiln holds components as the server rendered them, and render hooks add fields (amphora's `componentVariation`, for one) that stored data doesn't have. A revision read before the tab found out (again) that it missed changes is never trusted. Saves also send the gap their revision comes from (`X-Clay-Collab-Gap`): if amphora has started a new gap since, it answers 412 with its current data and gap, so even a tab that hasn't synced since the store came back merges instead of overwriting (and then catches up). Saves that couldn't reach the CMS at all (no answer; a 403 that isn't amphora's JSON, i.e. a gateway or proxy's; 502/503/504) are held by `core-data/connection.js` (`holdWhileUnreachable`) and retried, with the headers they were built with, instead of failing and reverting; `state.ui.heldSaves` counts them. While syncs can't reach the CMS, kiln checks every 3 seconds instead of backing off. A tab's unguarded saves are also kept in localStorage until amphora has them, so closing the tab can't lose the report. A catch-up waits for one more successful sync first, so changes the feed can name arrive that way ("Updated by Ada") and only the rest are shown as "Updated while you were reconnecting"; catch-ups run at most every 30 seconds. Anything that couldn't be re-read (or a merged save that couldn't be shown) is re-read again on its own, backing off from 30 seconds to 5 minutes; until then saving it merges with the server's copy. Kiln never reloads the page or asks the editor to. Saves that came back without a revision are also reported to amphora on the next sync (`unguarded`), so their revisions move on even if the instance that took them restarted.

Only one person edits a field at a time (`locks.js`). Each tab's presence says what it has open, how long since it last changed it (`quiet`) and, while it's taking something over, that it's asking for it (`claim`); amphora adds when each tab last synced (`seen`, server time). Before opening a form, kiln checks who else has an overlapping one open (same component, and the same field or a whole-component form): if they're working on it (changed it within `takeoverAfter`, 60 s by default, set in amphora; or typing; or asking for it themselves) it says so and opens nothing; if they've gone quiet (that long without changes, tab in the background or idle, or no sync from them for 15 s) it offers to take over. Taking over is a request: kiln closes whatever this tab had open, puts a `claim` for the field in its presence, and the holder's own tab, on its next sync, saves its form, closes it, and only then reports that it no longer has it. A tab with a form open syncs at least every 5 s, even in the background, so this takes a few seconds at most. Once the holder lets go (or after 10 s without an answer, or right away if they'd stopped syncing), kiln re-reads the component and opens the form, so it starts from the holder's saved text. A holder that's working on it after all (they typed before they saw the request) keeps it, and the newcomer is told they're editing it. A tab also hands over (if its user is quiet) when it finds someone actively editing what it has open, which covers coming back from sleep with a form still open ("Grace Hopper is editing Paragraph now — your changes were saved"). Two people taking over at once: the lower tab id goes first. None of this is enforced by the server, and it never blocks anyone when presence can't be read (reconnecting, or no sync for 30 s): the revision checks and merging below still catch whatever slips through, e.g. a holder whose background tab the browser has slowed down so much that it misses the 10 s and saves later.

All of this lives in `lib/collab/`. Hooks into the rest of kiln, all no-ops when collaboration is off:

| Where | What |
| --- | --- |
| `edit.js` | starts collaboration after the page is decorated |
| `component-data/actions.js`, `page-data/actions.js` | saves go through `collab/save.js` (revision + merge) |
| `forms/actions.js` | closing a form saves only the fields you changed |
| `decorators/actions.js` | one person per field: "is editing this" / "Take over" before opening a form |
| `undo/actions.js` | `rebaseHistory` keeps other people's changes out of undo |
| `core-data/api.js` | every request names its tab (`X-Clay-Collab-Session`) |
| `toolbar/edit-toolbar.vue` | presence bar and page layer |

## For plugin authors

* `state.collab` is `null` unless collaboration is on. When on: `{ session, connected, failures, others, activity, pending, flashes, claim }` (`claim`: the field this tab is taking over, while it waits).
* New mutations you can subscribe to: `COLLAB_START`, `COLLAB_SYNCED`, `COLLAB_SYNC_FAILED`, `COLLAB_ACTIVITY`, `COLLAB_PENDING`, `COLLAB_PENDING_DONE`, `COLLAB_FLASH`, `COLLAB_FLASH_DONE`, `COLLAB_CLAIM`, `COLLAB_STOP`. A flash or pending change with no `user` (pending: `by.reconnecting`) is one kiln caught up on while reconnecting.
* While collaborating, `UPDATE_COMPONENT` and `REVERT_COMPONENT` on the layout also update `state.layout.data` (where kiln reads layout data from), so saves are merged against what's on screen. Remote layout changes re-render only the layout lists that changed, from the page's server html.
* Remote changes are applied with the same mutations as local ones (`UPDATE_COMPONENT`, `RENDER_COMPONENT` with `snapshot: false`, `UPDATE_PAGE`, `UPDATE_PAGE_STATE`), so plugins that react to those keep working.
* Save through kiln (`store.dispatch('saveComponent', ...)`, `savePage`) to get revision checks and merging. Plugins that `PUT` to the API directly still work, but their writes are unconditional (last one wins), as before.
* Clicks inside elements with the `kiln-collab` class don't close the current form.
* Opening forms through `store.dispatch('focus', ...)` gets the one-person-per-field check; dispatching `openForm` directly skips it.
